# FaceTomato 四大功能流程说明

本文档说明项目中以下四个核心功能的业务流程和技术调用链：

- JD 匹配分析
- 简历优化
- 模拟面试
- 面试复盘

相关前端入口：

- 简历解析：`/resume`
- 简历优化 / JD 匹配分析：`/diagnosis`
- 模拟面试：`/interview`
- 面试报告 / 面试复盘：`/interview-review`

## 0. 全局前置流程：简历解析

这四个能力都依赖结构化简历数据，因此用户通常需要先完成简历解析。

1. 用户进入「简历解析」页面，上传 PDF、DOCX、JPG、JPEG、PNG、TXT、Markdown 等格式的简历。
2. 前端生成本地预览：
   - PDF 用 `pdfjs-dist` 渲染预览。
   - 图片直接展示。
   - 文本类文件直接读取文本预览。
3. 前端调用 `POST /api/resume/parse` 上传文件。
4. 后端校验文件类型和大小，然后根据文件类型选择解析策略：
   - 可直接抽文本的文件会抽取文本后交给 LLM 结构化。
   - 图片或需要 OCR 的场景会结合 OCR / LLM 解析。
   - 如果配置了运行时 OCR Key，会优先使用增强 OCR 能力。
5. 后端返回结构化 `ResumeData` 和解析元信息 `ParseMeta`。
6. 前端把解析结果写入 `resumeStore`，供后续 JD 匹配、简历优化、模拟面试使用。
7. 如果重新上传或清空简历，前端会同时清空旧的优化分析结果，避免旧 JD / 旧建议和新简历混用。

核心代码位置：

- 前端页面：`frontend/src/pages/ResumePage.tsx`
- 简历状态：`frontend/src/store/resumeStore.ts`
- 前端 API：`frontend/src/lib/api.ts`
- 后端路由：`backend/app/api/routes/resume.py`
- 后端解析服务：`backend/app/services/pdf_parser.py`、`backend/app/services/resume_extractor.py`

## 1. JD 匹配分析流程

JD 匹配分析发生在「简历优化」页面，但只有用户填写 JD 时才会进入 JD 定向分析模式。

### 1.1 用户流程

1. 用户先在「简历解析」页面上传并完成简历解析。
2. 用户进入「简历优化」页面。
3. 页面左侧展示已解析的结构化简历。
4. 用户在右侧输入目标岗位 JD。
5. 用户点击「开始匹配分析」。
6. 页面进入分析状态，并切换到 JD 相关分析视图。
7. 分析完成后，用户可以查看：
   - JD 解析结果
   - 匹配分数
   - 各类要求的匹配情况
   - 缺口项
   - JD 定向的简历优化建议

### 1.2 前端调用链

入口组件是 `frontend/src/components/optimization/InputPhase.tsx`。

当 `jdText.trim().length > 0` 时，前端执行 JD 模式：

1. 调用 `startAnalysis()`，将 `optimizationStore.status` 设置为 `loading`。
2. 调用 `extractJdData(jdText)`：
   - 请求 `POST /api/jd/extract`
   - 返回结构化 `JDData`
3. 写入 `jdData`，并将活动页签切到 `jdAnalysis`。
4. 调用 `setAnalysisComplete()`，让页面进入分析展示态。
5. 并行触发三类分析：
   - `getJdOverview(...)` -> `POST /api/resume/jd/overview`
   - `getJdSuggestions(...)` -> `POST /api/resume/jd/suggestions`
   - `getJdMatch(...)` -> `POST /api/resume/jd/match`
6. 各接口结果陆续写入 `optimizationStore`：
   - `overview`
   - `suggestions`
   - `matchReport`

### 1.3 后端处理流程

`POST /api/jd/extract`

1. 校验 JD 文本不能为空，且长度不能超过 30000 字符。
2. 根据运行时配置创建 `JDExtractor`。
3. 调用 LLM 抽取结构化 JD。
4. 返回 `JDData`，字段包括：
   - `basicInfo.jobTitle`
   - `basicInfo.jobType`
   - `basicInfo.location`
   - `basicInfo.company`
   - `requirements.degree`
   - `requirements.experience`
   - `requirements.techStack`
   - `requirements.mustHave`
   - `requirements.niceToHave`
   - `requirements.jobDuties`

`POST /api/resume/jd/match`

1. 校验 `jdText` 或 `jdData` 至少存在一个。
2. 如果只有 `jdData`，后端会把结构化 JD 渲染成纯文本。
3. 创建 `JDResumeMatcher`。
4. 调用 `matcher.match(resumeData, jdText, jdData)`。
5. 返回匹配结果：
   - 总分、满分、百分比
   - 分类得分
   - 每条 JD 要求的匹配状态、理由、证据
   - 缺口项

### 1.4 结果展示

前端将后端返回的 JD 匹配结果转换为 `MatchReport`：

- `overallScore`：总得分
- `maxScore`：满分
- `percent`：匹配百分比
- `headline`：摘要结论
- `scoreBreakdown`：分类得分
- `requirements`：逐条要求匹配
- `gaps`：缺口项

分类权重在前端 `optimizationStore` 中也有一份展示用配置：

- 必备条件 `mustHave`：0.5
- 学历要求 `degree`：0.5
- 经验要求 `experience`：0.5
- 加分项 `niceToHave`：0.2
- 技术栈 `techStack`：0.2
- 岗位职责 `jobDuties`：0.1

核心代码位置：

- 输入与触发：`frontend/src/components/optimization/InputPhase.tsx`
- 分析状态：`frontend/src/store/optimizationStore.ts`
- 前端 API：`frontend/src/lib/api.ts`
- JD 抽取路由：`backend/app/api/routes/jd.py`
- JD 匹配路由：`backend/app/api/routes/jd_optimization.py`
- 匹配服务：`backend/app/services/jd_resume_matcher.py`
- Prompt：`backend/app/prompts/jd_prompts.py`、`backend/app/prompts/jd_optimization_prompts.py`

## 2. 简历优化流程

简历优化和 JD 匹配共用「简历优化」页面。区别是：用户不填写 JD 时走通用简历优化；填写 JD 时走 JD 定向简历优化。

### 2.1 通用简历优化

用户不填写 JD 时：

1. 用户完成简历解析。
2. 进入「简历优化」页面。
3. JD 输入框留空。
4. 点击「开始通用分析」。
5. 前端并行请求：
   - `getResumeOverview(parsedResume)` -> `POST /api/resume/overview`
   - `getResumeSuggestions(parsedResume)` -> `POST /api/resume/suggestions`
6. 概览接口返回后，页面进入分析态。
7. 建议接口返回后，页面展示按模块拆分的修改建议。

通用优化产出：

- 简历摘要
- 亮点
- 风险点
- 适配岗位画像
- 按模块拆分的修改建议

### 2.2 JD 定向简历优化

用户填写 JD 时，简历优化会和 JD 匹配分析一起执行。

1. 用户填写 JD 并点击「开始匹配分析」。
2. 前端先抽取结构化 JD。
3. 前端并行请求：
   - `POST /api/resume/jd/overview`
   - `POST /api/resume/jd/suggestions`
   - `POST /api/resume/jd/match`
4. 页面展示 JD 匹配报告，同时展示 JD 定向的简历修改建议。

JD 定向优化更强调：

- 简历内容是否覆盖 JD 必备项
- 技术栈、项目经历、工作经历是否能作为证据
- 缺口如何补充或改写
- 如何围绕目标岗位重排表达重点

### 2.3 前端状态流转

`optimizationStore.status` 有四种状态：

- `input`：等待输入 JD 或开始通用分析
- `loading`：分析中
- `analysis`：分析结果展示中
- `error`：分析失败

`suggestionsStatus` 单独表示建议生成状态：

- `idle`
- `loading`
- `ready`
- `error`

这样设计后，即使概览已经返回，建议生成仍可以继续独立加载。

### 2.4 后端处理流程

通用简历优化路由：

- `POST /api/resume/overview`
- `POST /api/resume/suggestions`

处理逻辑：

1. 请求体继承 `ResumeData`，可附带运行时模型配置。
2. 后端解析运行时配置。
3. 创建 `ResumeOptimizer`。
4. 分别调用：
   - `optimizer.get_overview(...)`
   - `optimizer.get_suggestions(...)`
5. 返回结构化概览或建议。

JD 定向简历优化路由：

- `POST /api/resume/jd/overview`
- `POST /api/resume/jd/suggestions`

处理逻辑：

1. 校验 JD 必填。
2. 规范化 JD 文本。
3. 创建 `JDResumeMatcher`。
4. 分别调用：
   - `matcher.get_jd_overview(...)`
   - `matcher.get_jd_suggestions(...)`
5. 返回 JD 定向概览或建议。

核心代码位置：

- 页面入口：`frontend/src/pages/DiagnosisPage.tsx`
- 输入阶段：`frontend/src/components/optimization/InputPhase.tsx`
- 分析展示：`frontend/src/components/optimization/AnalysisPhase.tsx`
- 状态管理：`frontend/src/store/optimizationStore.ts`
- 通用优化路由：`backend/app/api/routes/resume_optimization.py`
- JD 定向优化路由：`backend/app/api/routes/jd_optimization.py`
- 通用优化服务：`backend/app/services/resume_optimizer.py`
- JD 定向服务：`backend/app/services/jd_resume_matcher.py`
- Prompt：`backend/app/prompts/resume_optimization_prompts.py`、`backend/app/prompts/jd_optimization_prompts.py`

## 3. 模拟面试流程

模拟面试是一个基于结构化简历、JD、岗位类型、岗位领域生成的流式对话流程。项目采用“前端保存会话快照、后端无状态处理单轮流式请求”的设计。

### 3.1 用户流程

1. 用户先完成简历解析。
2. 用户进入「模拟面试」页面。
3. 用户选择：
   - 面试岗位类型
   - 面试岗位领域
4. 用户填写岗位 JD。
5. 点击「开始模拟面试」。
6. 系统进入创建阶段：
   - 检索相关面经
   - 生成面试计划
   - 初始化面试官
7. 面试会话创建完成后，进入聊天界面。
8. 用户点击发送或使用语音输入提交回答。
9. 后端先对候选人回答做反思分析，再生成面试官下一问。
10. 面试按计划轮次推进，达到结束条件后状态变为 completed。
11. 用户可以导出对话记录，也可以重新开始。

### 3.2 创建会话流程

前端调用：

`POST /api/mock-interview/session/stream-create`

这是 SSE 流式接口，前端通过 `streamCreateMockInterviewSession` 监听事件。

后端 `MockInterviewService.stream_create_session(...)` 依次发送：

1. `progress: retrieving_evidence`
   - 前端显示「正在检索相关面经」。
2. 后端检索面经证据：
   - 如果 RAG 可用，调用 RAG 检索。
   - 如果 RAG 不可用，按岗位领域、面试类型、公司等条件从题库中降级筛选。
3. `developer_trace: retrieval`
   - 记录检索 query、过滤链、命中结果、耗时等调试信息。
4. `progress: generating_plan`
   - 前端显示「正在生成面试计划」。
5. 后端结合 JD、简历、检索面经生成结构化面试计划。
6. `developer_trace: plan_generation`
   - 记录计划生成过程和耗时。
7. `session_created`
   - 返回会话 ID、岗位类型、领域、JD、简历快照、检索结果、面试计划、初始面试状态、过期时间等。
8. `done`
   - 标记会话创建完成。

前端收到 `session_created` 后会：

- 初始化 `mockInterviewStore`
- 保存可恢复快照到浏览器本地
- 设置 URL 查询参数
- 准备进入聊天流程

### 3.3 面试对话流程

前端调用：

`POST /api/mock-interview/session/{sessionId}/stream`

请求中携带完整上下文：

- `mode`：`start` 或 `reply`
- `interviewType`
- `category`
- `jdText`
- `jdData`
- `resumeSnapshot`
- `retrieval`
- `interviewPlan`
- `interviewState`
- `messages`
- 用户本轮回答 `message`

后端每次都会用请求中的上下文构造临时会话，因此后端不依赖持久化会话状态。

当 `mode = start`：

1. 后端直接生成面试官开场问题。
2. 流式返回 `message_start`、`message_delta`、`message_end`、`done`。

当 `mode = reply`：

1. 后端校验回答长度不超过限制。
2. 生成并返回 `user_message` 事件。
3. 返回 `answer_analysis_started`，提示前端进入“回答分析中”。
4. 调用 reflection LLM，对候选人回答进行分析，返回：
   - 深度评分
   - 真实性评分
   - 完整性评分
   - 逻辑评分
   - 是否继续当前轮
   - 建议追问
5. 返回 `reflection_result` 和 `developer_trace: reflection`。
6. 如果当前轮需要结束：
   - 非最后一轮：返回 `round_transition`，进入下一轮 topic。
   - 最后一轮：设置 `closed = true`，准备结束面试。
7. 调用面试官生成模型，流式返回下一条面试官消息：
   - `message_start`
   - `message_delta`
   - `message_end`
8. 返回 `developer_trace: interviewer_generation`。
9. 返回 `done`，状态为：
   - `ready`：可继续回答
   - `completed`：面试结束

### 3.4 会话保存与恢复

模拟面试会话主要保存在浏览器本地：

- 创建中会话保存为 pending session。
- 已创建会话保存为 recoverable session。
- 每次用户回答、AI 回复、轮次切换、开发者 trace 都会更新本地快照。
- 左侧导航可以展开历史面试并恢复会话。
- 当前浏览器缓存清理后，历史面试会丢失。

### 3.5 语音输入

模拟面试页面会调用：

`GET /api/speech/status`

如果运行时设置中配置了语音服务 Key 且后端可用，前端会启用麦克风输入。语音识别的中间结果和最终结果会写入回答输入框，用户仍需提交后才进入面试流。

核心代码位置：

- 页面入口：`frontend/src/pages/MockInterviewPage.tsx`
- 状态管理：`frontend/src/store/mockInterviewStore.ts`
- 会话本地恢复：`frontend/src/lib/mockInterviewRecovery.ts`
- 前端流式 API：`frontend/src/lib/mockInterviewApi.ts`
- 后端路由：`backend/app/api/routes/mock_interview.py`
- 后端服务：`backend/app/services/mock_interview_service.py`
- RAG 服务：`backend/app/services/interview_rag_service.py`
- 题库服务：`backend/app/services/interview_service.py`
- Prompt：`backend/app/prompts/mock_interview_prompts.py`

## 4. 面试复盘流程

面试复盘基于已完成的模拟面试快照生成。它不直接依赖后端保存的会话，而是从前端本地可恢复会话中找到 completed 的模拟面试，再把快照发给后端评估。

### 4.1 用户流程

1. 用户先完成一场模拟面试。
2. 模拟面试状态必须是 completed，或 `interviewState.closed === true`。
3. 用户进入「面试报告」页面。
4. 页面列出当前浏览器中可复盘的历史模拟面试。
5. 用户打开某条记录。
6. 如果尚未生成报告，点击「生成报告」。
7. 页面显示 Topic 级生成进度。
8. 报告生成完成后，用户可以查看：
   - 总体评分
   - 总结
   - 优势
   - 风险
   - 优先改进建议
   - 每个 Topic 的评分、核心问题、预览评价和主要问题
9. 用户点击某个 Topic 后，会按需生成深度分析。
10. 用户可以在右侧「面试回复打磨」中继续追问，让系统针对该 Topic 优化回答。

### 4.2 复盘列表来源

前端 `interviewReviewApi` 会读取模拟面试本地快照：

- 只展示 completed 或 closed 的 recoverable session。
- 如果本地已有复盘报告缓存，则展示 ready 状态和分数。
- 如果没有报告，则展示 pending 状态。

缓存 Key：

- 报告：`face-tomato-interview-review-reports-v3`
- 追问对话：`face-tomato-interview-review-conversations-v3`
- 生成中状态：`face-tomato-interview-review-generating-v2`
- 生成进度：`face-tomato-interview-review-generating-progress-v2`

### 4.3 生成报告流程

前端调用：

`POST /api/interview-reviews/{sessionId}/generate/stream`

请求体是完整的 `MockInterviewSessionSnapshot`，包含：

- 会话 ID
- 岗位类型和领域
- JD 文本和结构化 JD
- 简历快照
- 检索结果
- 面试计划
- 面试状态
- 全量消息记录
- 运行时模型配置

后端 `InterviewReviewService.generate_review_events(...)` 处理：

1. 校验 snapshot 是否存在。
2. 校验会话是否可复盘：
   - `snapshot.status == "completed"`，或
   - `snapshot.interviewState.closed is True`
3. 将 snapshot 转换为 `InterviewEvaluationAgentInput`。
4. 调用 `InterviewEvaluationAgent.evaluate_previews_with_progress(...)`。
5. 逐个 Topic 输出预览评价：
   - Topic 名称
   - 核心问题
   - Topic 分数
   - 预览总结
   - 关键问题
6. SSE 返回：
   - `start`
   - 多个 `topic_complete`
   - `done`
7. `done` 事件中返回完整 `ReviewSessionDetail`。
8. 前端把报告写入 localStorage。

### 4.4 Topic 深度分析流程

当用户选中某个 Topic 且报告已 ready，但该 Topic 尚无详情时，前端调用：

`POST /api/interview-reviews/{sessionId}/topics/{topicId}/generate-detail`

处理流程：

1. 前端携带 sessionId、topicId、snapshot 和运行时配置。
2. 后端再次校验会话可复盘。
3. 根据 `topicId` 解析 Topic 序号。
4. `InterviewEvaluationAgent` 构建 topic input。
5. 针对该 Topic 生成深度评估。
6. 返回 `ReviewTopicDetail`，包含：
   - 考察点
   - 实际回答片段
   - 采分点匹配状态
   - 优势
   - 短板
   - 建议
   - 优化回答
7. 前端写回本地报告缓存。

### 4.5 回答打磨流程

用户在「面试回复打磨」输入问题后，前端调用：

`POST /api/interview-reviews/{sessionId}/topics/{topicId}/optimize`

请求包含：

- 当前 Topic 详情
- 用户消息
- 当前 Topic 的历史对话
- 运行时配置

后端处理：

1. 构造 `ReviewTopicOptimizationInput`。
2. 调用 LLM 生成结构化 `ReviewTopicOptimizationResult`。
3. 如果 LLM 失败，使用 fallback 生成基础建议。
4. 返回 assistant 消息、优化回答、建议列表、引用和证据。
5. 前端把对话写入 localStorage。

核心代码位置：

- 页面入口：`frontend/src/pages/InterviewReviewPage.tsx`
- 前端复盘 API 与缓存：`frontend/src/lib/interviewReviewApi.ts`
- 后端路由：`backend/app/api/routes/interview_reviews.py`
- 后端服务：`backend/app/services/interview_review_service.py`
- 评估 Agent：`backend/app/services/interview_evaluation_agent.py`
- Prompt：`backend/app/prompts/interview_review_prompts.py`

## 5. 四个功能之间的关系

整体依赖关系如下：

1. 简历解析是基础能力。
2. 简历优化依赖结构化简历。
3. JD 匹配分析依赖结构化简历和 JD。
4. JD 定向简历优化依赖结构化简历和 JD。
5. 模拟面试依赖结构化简历、岗位类型、岗位领域和 JD。
6. 面试复盘依赖已完成的模拟面试本地快照。

可以理解为：

```text
简历上传
  -> 简历解析
      -> 通用简历优化
      -> JD 匹配分析
      -> JD 定向简历优化
      -> 模拟面试
          -> 本地保存面试快照
              -> 面试复盘
                  -> Topic 深度分析
                  -> 回答打磨
```

## 6. 运行时配置影响

前端侧边栏底部提供「运行时设置」，可覆盖部分后端默认配置：

- 自定义 LLM Provider / API Key / Base URL / Model
- 简历 OCR API Key
- 语音输入 App Key / Access Key

这些配置会随请求传给后端：

- 简历解析：影响 LLM 和 OCR
- JD 抽取 / JD 匹配 / 简历优化：影响 LLM
- 模拟面试：影响计划生成、反思分析、面试官回复
- 面试复盘：影响报告生成、Topic 深度分析、回答打磨
- 语音输入：影响麦克风识别是否可用

如果用户不填写运行时配置，则使用后端默认配置。

## 7. 常见异常路径

简历解析：

- 文件类型不支持：返回 `UNSUPPORTED_FILE_TYPE`
- 文件过大：返回 `FILE_TOO_LARGE`
- 内容无法抽取：返回 `EMPTY_CONTENT`
- 上传内容不是简历：返回 `INVALID_RESUME_CONTENT`
- OCR 或 LLM 失败：返回 `OCR_FAILED` / `LLM_FAILED`

JD 分析：

- JD 为空：返回 `EMPTY_TEXT` 或 `JD_REQUIRED`
- JD 超长：返回 `TEXT_TOO_LARGE`
- 内容不是正常 JD：返回 `INVALID_JD_CONTENT`
- LLM 失败：返回 `LLM_FAILED` 或对应 JD 分析失败码

模拟面试：

- 未解析简历时，页面会提示先上传简历。
- 未选择岗位类型或岗位领域时，不能开始。
- JD 为空时，页面会弹窗要求补充 JD。
- 创建面试计划失败时，前端展示错误。
- 单轮回答超过长度限制时，后端拒绝。
- 面试已完成后，不能继续发送回答。

面试复盘：

- 未完成的模拟面试不能生成复盘。
- 本地快照不存在时，后端返回 not found。
- 复盘生成中断时，前端会清理陈旧生成状态并提示重新生成。
- 浏览器缓存被清理后，历史模拟面试和复盘报告都会丢失。
