## 一、简历优化功能重构

### 问题现象

用户强调：

```text
优化只是给出建议，而不是直接基于用户的简历直接进行修改。
我们做的是基于 JD 的要求针对简历给出合理的建议。
```

原流程中存在几个体验问题：

- 页面进入后会展示上一次优化后的结果，容易让用户误以为当前已经在编辑某个旧优化稿。
- 「优化预览」对当前业务价值不高，容易把用户引导到“直接改简历”的理解上。
- 「修改建议」只显示工作经历、项目经历等模块名，用户无法快速定位到简历中对应的原始段落。
- 优化结果没有清晰保存入口，也没有“一份简历 + 一个岗位 JD 对应一条优化记录”的历史视图。
- 优化记录名称不能编辑。

- 新增「新增优化」入口，用于清空目标岗位、JD 和当前结果，开始新一轮分析。

## 四、后端端口占用问题说明

### 问题现象

后端启动时报错：

```text
Error: listen EADDRINUSE: address already in use :::8001
```

但用户测试接口仍然能够正常响应。

### 判断原因

这说明 `8001` 端口上已经有一个后端 Node/Nest 进程在运行。再次启动后端时，新进程无法绑定同一个端口，因此抛出 `EADDRINUSE`。

接口能正常响应，是因为旧的后端进程仍在监听并提供服务。

### 处理说明

用户表示希望自己打开后端，因此本轮后续没有继续启动后端服务，只进行代码构建和前端部署验证。

## 七、注意事项

### 简历优化

- 当前优化功能定位为“建议生成”，不是“直接改写简历”。
- 修改建议需要继续围绕用户简历原文定位，而不是暴露数据库 JSON。
- 历史记录必须由用户主动点击查看，进入页面默认保持新优化状态。

### 岗位推荐

- 已保存岗位中的匹配分已去除，但推荐列表中如仍需要排序，可继续保留内部评分。
- 备注信息是用户自定义内容，不应再叫岗位类型。
- 手动添加岗位创建后应和推荐保存岗位走同一套后端 Job 数据。

### 模拟面试

- 专业模式第一阶段建议先把“追问生成”升级为“下一步面试动作决策”。
- 不建议一开始就做多次 LLM 调用的重型多 Agent，避免延迟和稳定性问题。
- 评估信息应后台静默记录，不要在面试过程中频繁打断候选人。
