## 1. 当前背景

当前项目由两套主要工程组成：

- 前端：`frontEnd`
- 后端：`ai-job-backend`
- 数据库：PostgreSQL，通过 Prisma 访问

本轮遇到的核心问题不是单点报错，而是前端、后端、数据库三层之间的“数据模型没有完全统一”：

1. 前端已经换成新的移动端 UI，页面结构、交互入口、功能块位置都发生了变化。
2. 后端本身已有一套 NestJS + Prisma 的接口和数据模型。
3. 当前数据库里存在旧版蛇形命名表，例如 `users`、`job_matches`、`knowledge_chunks` 等。
4. Prisma 当前 schema 中又存在一批新模型表，例如 `"User"`、`"Resume"`、`"Job"`、`"InterviewSession"`、`"ReviewReport"` 等。
5. 为了解决注册登录报错，认证逻辑已经临时改为使用旧表 `users`。
6. 但其他业务模块仍大量使用 Prisma 新模型表，导致当前处于“认证使用旧表、业务使用新表”的混合状态。

这个状态可以临时调通部分功能，但不适合作为长期工程结构。

## 3. 当前最大问题：数据库表模型混用

### 3.1 注册报错的根因

之前注册时报错：

```text
The table public.User does not exist in the current database.
```

原因是后端原本调用：

```ts
this.prisma.user.findUnique(...)
```

这个 Prisma 模型默认对应数据库表：

```text
"User"
```

但当前数据库实际存在的是旧表：

```text
users
```

因此注册时后端找不到 `"User"` 表。

### 3.2 当前临时修复方式

已在 Prisma schema 中增加旧表映射：

```prisma
model LegacyUser {
  id           String   @id @default(cuid())
  email        String?  @unique
  phone        String?  @unique
  name         String?
  avatarUrl    String?  @map("avatar_url")
  role         String   @default("user")
  status       String   @default("active")
  passwordHash String?  @map("password_hash")
  createdAt    DateTime @default(now()) @map("created_at")
  updatedAt    DateTime @updatedAt @map("updated_at")

  @@map("users")
}
```

认证模块已改为：

```ts
this.prisma.legacyUser
```

因此当前用户注册和登录会进入数据库旧表：

```text
users
```

### 3.3 当前风险

当前只有认证模块切到了 `users`，但后端其他模块仍使用新 Prisma 表：

| 模块 | 当前主要 Prisma 模型 | 数据库表倾向 |
|---|---|---|
| 认证注册登录 | `LegacyUser` | `users` |
| 用户管理 | `User` | `"User"` |
| 个人资料 | `UserProfile` | `"UserProfile"` |
| 简历 | `Resume`、`ResumeVersion`、`ResumeExport` | `"Resume"` 等 |
| 岗位 | `Job` | `"Job"` |
| 模拟面试 | `InterviewSession` | `"InterviewSession"` |
| 面试报告 | `ReviewReport` | `"ReviewReport"` |
| 真实面试知识库 | `InterviewKnowledgeBase`、`RealInterviewRecord` | `"InterviewKnowledgeBase"`、`"RealInterviewRecord"` |

风险点：

1. JWT 中的用户 ID 来自 `users.id`，当前是字符串。
2. 很多业务服务仍按 `User.id` 的数字 ID 设计。
3. 如果带着 `users.id` 调用简历、岗位、报告等接口，可能出现类型不匹配、查不到用户、外键不一致等问题。
4. 如果直接删除旧表 `users`，登录注册会立刻不可用。

结论：

```text
当前不能直接删除 users。
其他旧蛇形表是否能删除，要等表模型统一和数据迁移完成后再判断。
```

## 4. 是否需要前后端接口文档

需要。

前端、后端、数据库联通是整个程序运行的底层逻辑。尤其当前项目已经换过前端 UI，后端又存在新旧表混用，如果没有接口文档，后续很容易出现这些问题：

- 前端页面按钮不知道应该调用哪个后端接口。
- 后端接口返回字段和前端组件需要字段不一致。
- 后端写入的数据库表不是预期表。
- 数据库里有数据，但前端页面读不到。
- 旧表、新表同时存在，无法判断哪个是真正运行表。
- 做 ASR、知识库、RAG 这类长链路功能时，很难定位数据停在哪一步。

因此建议维护一份“前端交互 -> 后端接口 -> Service 处理 -> Prisma 模型 -> 数据库表”的接口文档。

下面先记录当前已知主链路。

### 5.13 当前 RAG 检索

当前后端有 RAG 相关服务：

- `InterviewRagService`
- `local-embedding.util.ts`

当前方式：

1. 从 `RealInterviewRecord.chunks` 读取 chunks。
2. 用本地 hash 算法生成 256 维 embedding。
3. 在内存中做 cosine similarity。
4. 返回相似 chunks。

当前不是正式向量数据库，因为：

- 没有 `pgvector` 查询。
- 没有 `knowledge_chunks.embedding` 字段。
- 没有把 chunk embedding 存进数据库。
- 没有使用 SQL 向量距离排序。

正式 RAG 应该改成：

```text
RealInterviewRecord.structuredContent/chunks
-> knowledge_items
-> knowledge_chunks
-> embedding vector
-> pgvector 相似度检索
-> RAG prompt
-> 大模型回答
```

| 大模型清洗 | 部分满足 | `structuredContent`，但没有单独 clean transcript 字段 |

结论：

```text

```

## 7. 旧蛇形表是否可以删除

当前建议：

```text
不要现在删除。
```

原因：

1. `users` 当前已经被登录注册使用。
2. `knowledge_items`、`knowledge_chunks` 可能正好适合作为正式知识库和向量 RAG 的落点。
3. `interview_reviews`、`review_transcripts`、`review_qa_pairs`、`review_insights` 可能适合承载真实面试复盘的细粒度数据。
4. 当前业务表还没有完成统一迁移，删除旧表会增加排查难度。
5. 如果旧表里有历史数据，删除会造成不可逆数据损失。

可以删除的前提：

1. 已备份数据库。
2. 已确认前端没有直接依赖旧接口。
3. 已确认后端代码没有引用旧表。
4. 已确认 Prisma schema 和数据库表命名统一。
5. 已完成旧数据迁移或确认旧数据无价值。

## 8. 建议的数据库统一方向

当前有两个方向，必须选择一个作为主线。

### 方向 A：统一使用 Prisma 新表

特点：

- 使用 `"User"`、`"Resume"`、`"Job"`、`"InterviewSession"`、`"ReviewReport"` 等。
- 把认证逻辑从 `users` 改回 `User`。
- 删除或迁移旧蛇形表。

优点：

- 当前后端业务代码改动较少。
- Prisma 模型和代码默认一致。

缺点：

- 数据库表名会是 PascalCase + 引号风格，不太符合已有旧库习惯。
- 如果旧库已有大量数据，迁移成本较高。

### 方向 B：统一使用旧蛇形表

特点：

- 保留 `users`、`knowledge_items`、`knowledge_chunks` 等旧表。
- 在 Prisma schema 中使用 `@@map` 和 `@map` 映射旧表旧字段。
- 把所有业务服务逐步迁移到旧表模型。

优点：

- 更贴近当前数据库 Studio 里看到的旧库结构。
- 更适合继续使用 `knowledge_chunks` 做 pgvector RAG。
- 表名更符合 PostgreSQL 常见工程风格。

缺点：

- 后端服务需要逐个迁移。
- 需要认真梳理旧表字段和当前业务 DTO 的映射。

当前建议：

```text
更推荐方向 B：统一使用旧蛇形表，并通过 Prisma @@map/@map 做工程化映射。
```

理由：

- 用户已经明确希望“使用旧表 users 之类的表”。
- 当前数据库里已经存在旧蛇形表。
- 知识库和向量库天然适合用 `knowledge_items`、`knowledge_chunks`。
- 未来做 RAG 时，蛇形表更自然，也便于直接 SQL 调试。

### 12.1 现象

前端当前配置仍指向本机后端：


因此真实链路是：

```text
前端 -> http://localhost:3001 -> Windows 本机后端
Windows 本机后端 -> 保存到 D:\home\public\audio\user-1
后端生成了服务器公网 URL
DashScope 去 http://120.79.220.126:8001/audio/... 下载
服务器 /home/public/audio 没有该文件
ASR FILE_DOWNLOAD_FAILED
```

已在本机确认文件实际落在：

```text
D:\home\public\audio\user-1\1781533966929-c4502818-10b3-435b-a8b8-e94cfcbc157e.m4a
```

这说明文件上传功能本身触发了，但请求打到了本机后端，而不是服务器后端。
