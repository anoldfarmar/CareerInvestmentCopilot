# 职投 Copilot 知识库构建文档

本文档说明面试录音复盘结果如何进入数据库，用户知识库与面试复盘表、简历表、用户画像表之间是什么关系，以及如何直接基于 PostgreSQL + pgvector 构建正式 RAG 语义检索能力。

## 1. 先理清几个概念

职投 Copilot 里不要把所有内容都叫“知识库”。建议分成四层：

```txt
原始材料层
  -> 音频文件、ASR 原始 JSON、清洗稿、AI 复盘 JSON

业务记录层
  -> 一次真实面试复盘、一份简历、一个岗位 JD、一次模拟面试

知识条目层
  -> 高频问题、短板、改进建议、回答模板、技能缺口、公司岗位经验

检索增强层
  -> PostgreSQL + pgvector 语义召回、规则过滤、RAG 上下文拼接
```

面试复盘表记录的是“一场面试发生了什么”。  
用户知识库记录的是“这场面试沉淀出了哪些可复用经验”。  
RAG 检索层解决的是“下次模拟面试时，如何从历史经验里取出最相关的内容给大模型”。本项目既然目标明确包含个性化 RAG 模拟面试官，后端数据库主路线直接使用 PostgreSQL + pgvector，不再以 SQLite 作为知识库主路线。

## 2. 当前生成文件哪些需要入库

以当前 ASR + AI 复盘流程为例，目录中会生成这些文件：

```txt
data/腾讯音乐_数据科学.m4a
data/asr_results/腾讯音乐_数据科学_fun_asr.json
data/asr_results/腾讯音乐_数据科学_fun_asr.txt
data/asr_results/腾讯音乐_数据科学_fun_asr_speakers.txt
data/asr_results/腾讯音乐_数据科学_fun_asr_roles.txt
data/asr_results/腾讯音乐_数据科学_ai_review.json
data/asr_results/腾讯音乐_数据科学_clean_transcript.txt
data/asr_results/腾讯音乐_数据科学_ai_review_report.md
```

建议入库方式：

| 文件 | 是否入库 | 对应表 | 说明 |
| --- | --- | --- | --- |
| 原始音频 `.m4a` | 不把二进制直接塞数据库 | `files`、`review_audios` | 数据库存路径、大小、URL、hash，文件留在 uploads/public/对象存储 |
| `_fun_asr.json` | 入库或存文件引用 | `review_transcripts.asr_raw_json` / `asr_raw_file_id` | 原始 ASR 结果，较大时推荐存文件路径 |
| `_fun_asr.txt` | 可不单独入库 | `review_transcripts` | 纯文本可由 ASR JSON 再生成，非核心 |
| `_fun_asr_speakers.txt` | 入库 | `review_transcripts.speaker_text` | 保留说话人编号版本，便于排错 |
| `_fun_asr_roles.txt` | 入库 | `review_transcripts.role_text` | AI 复盘核心输入 |
| `_ai_review.json` | 入库 | 多张业务表 | 不能只存一个 JSON，要拆到复盘、问答、洞察、知识库 |
| `_clean_transcript.txt` | 入库 | `review_transcripts.clean_text` | 前端展示清洗稿 |
| `_ai_review_report.md` | 可选 | `files` 或不入库 | 展示产物，可由 JSON 重新生成 |

核心原则：

- 文件系统保存“大文件和可再生成文件”。
- 数据库保存“业务记录、结构化结果、检索字段和来源关系”。
- 不要把音频二进制、完整 Markdown 报告一股脑塞进数据库。

## 3. 一次面试复盘如何落库

当前 Prisma schema 已经有这些核心表：

```txt
users
user_profiles
files
interview_reviews
review_audios
review_transcripts
review_qa_pairs
review_insights
knowledge_items
tasks
ai_call_logs
resumes
job_descriptions
job_matches
mock_interview_sessions
mock_interview_messages
```

一次真实面试录音处理完成后，建议按下面顺序写库。

### 3.1 files

存原始音频文件元数据。

字段映射：

```txt
biz_type = interview_audio
original_name = 腾讯音乐_数据科学.m4a
storage_name = tencent_music_data_science.m4a
storage_path = uploads/audios/xxx.m4a
public_url = ASR 可访问 URL
mime_type = audio/mp4
size_bytes = 文件大小
status = ready
```

### 3.2 interview_reviews

存“一场面试复盘”的主记录。

从 `_ai_review.json.metadata` 映射：

```txt
company_name = metadata.company_name
position_name = metadata.job_title
interview_round = metadata.interview_round
source_type = audio
status = completed
overall_summary = metadata.overall_summary
raw_review_json = 完整 AI JSON 字符串
```

注意：`raw_review_json` 是兜底备份，不代表前端只读这个字段。前端高频展示字段应该拆到子表。

### 3.3 review_audios

建立复盘记录和音频文件之间的关系。

```txt
review_id = interview_reviews.id
file_id = files.id
duration_seconds = 可后续用 ffprobe 解析
```

### 3.4 review_transcripts

存转写过程和文本结果。

```txt
review_id = interview_reviews.id
asr_provider = dashscope
asr_model = fun-asr
asr_raw_json = _fun_asr.json 内容或文件引用
speaker_text = _fun_asr_speakers.txt
role_text = _fun_asr_roles.txt
clean_text = _clean_transcript.txt
role_mapping_json = {"0":"interviewer","1":"candidate"} 或中文角色映射
language_hints_json = ["zh","en"]
```

### 3.5 review_qa_pairs

把 `_ai_review.json.qa_pairs` 每一项拆成一行。

```txt
question = qa.question
answer_summary = qa.answer_summary
tags_json = qa.topics
weaknesses_json = qa.issue 非空时写入
improvement_advice = qa.improvement
order_no = 原数组顺序
```

这一表很重要。后续模拟面试可以直接读取历史真实问题，作为下一次模拟追问素材。

### 3.6 review_insights

把亮点、短板、改进建议、下一步行动拆成洞察表。

映射建议：

```txt
strengths[] -> type = strength
weaknesses[] -> type = weakness
improvement_advice[] -> type = advice
next_actions[] -> type = next_action
```

例如：

```txt
type = weakness
title = "embedding 原理掌握不足"
content = "缺乏对词嵌入、向量空间、训练目标的基本认知"
severity = high
tags_json = ["embedding", "向量检索", "机器学习基础"]
```

### 3.7 knowledge_items

这是“用户知识库”的核心表。它不是简单复制整场复盘，而是把可复用的知识点沉淀出来。

来源：

```txt
_ai_review.json.knowledge_items
qa_pairs 中 issue / improvement 非空的题目
weaknesses
improvement_advice
next_actions
```

建议类型：

```txt
interview_question
weakness
improvement_advice
skill_gap
answer_template
company_note
project_evidence
```

字段映射：

```txt
user_id = 当前用户
source_type = review
source_id = interview_reviews.id
source_review_id = interview_reviews.id
type = 条目类型
title = 标题
content = 具体内容
summary = 一句话摘要
tags_json = 标签数组
priority = 0/1/2/3
mastery_level = weak / improving / mastered
status = active
```

## 4. 模拟面试官需要读哪些数据

你理解得基本对。模拟面试官不是只读知识库，而是读“用户画像 + 简历 + 岗位 + 历史复盘 + 知识库”的组合。

推荐读取顺序：

```txt
1. users / user_profiles
   -> 用户基础画像、目标方向、技能标签

2. resumes
   -> 当前简历结构化信息、项目经历、实习经历、技能栈

3. job_descriptions / job_matches
   -> 本次模拟面试对应岗位 JD、匹配差距、岗位能力要求

4. interview_reviews
   -> 历史真实面试整体表现、公司岗位、轮次、总结

5. review_qa_pairs
   -> 历史真实问题、回答摘要、被追问点、表现短板

6. knowledge_items
   -> 可复用短板、改进建议、回答模板、高频问题、技能缺口
```

模拟面试 Prompt 的上下文建议分层拼接：

```txt
用户画像摘要
当前简历摘要
目标岗位 JD 摘要
历史短板 Top 5
历史高频问题 Top 5
本次要重点训练的知识点 / 表达问题
```

不要把所有历史面试全文都塞给模型。上下文太长会贵、慢、乱，也容易让模型抓不到重点。

## 5. 为什么直接使用 PostgreSQL + pgvector

结论：

```txt
PostgreSQL 负责业务主数据和结构化过滤。
pgvector 负责 embedding 向量相似度召回。
Prisma 负责常规业务表读写。
raw SQL 负责 vector 字段和相似度查询。
```

这样做不是绕弯，而是把“业务数据库”和“语义检索”放在同一个 PostgreSQL 体系里：

```txt
PostgreSQL 普通表
  -> users、resumes、interview_reviews、knowledge_items 等业务数据

pgvector 向量字段
  -> knowledge_chunks.embedding，用于语义召回

SQL WHERE 条件
  -> user_id、status、type、tags、source_type 等规则过滤

vector distance
  -> 在候选知识片段中按语义相似度排序
```

为什么不只用向量库：

- 向量库擅长找相似文本，但不负责完整业务关系。
- 用户隔离、来源追踪、删除归档、掌握程度、优先级、岗位关联仍需要结构化数据库。
- 模拟面试的个性化不是只靠“相似”，还要知道这条知识属于谁、来自哪场面试、是否仍有效、优先级多高。

因此本项目的正式路线是：

```txt
PostgreSQL = 主数据库
pgvector = PostgreSQL 内的 RAG 语义检索扩展
```

## 6. 知识库表设计：knowledge_items 与 knowledge_chunks

### 6.1 knowledge_items

`knowledge_items` 是知识条目主表，负责业务管理，不直接承担长文本切片检索。

它回答：

```txt
这条知识属于谁？
来自哪次面试？
是什么类型？
优先级高不高？
用户掌握了吗？
是否归档或删除？
```

典型字段：

```txt
id
user_id
source_type
source_id
source_review_id
type
title
content
summary
tags_json
priority
mastery_level
status
created_at
updated_at
```

### 6.2 knowledge_chunks

`knowledge_chunks` 是 RAG 检索表，负责把知识条目、问答、简历经历、岗位要求切成可召回片段。

建议新增表：

```txt
knowledge_chunks
  id
  user_id
  knowledge_item_id
  source_type
  source_id
  chunk_text
  embedding vector(维度)
  tags_json
  token_count
  status
  created_at
```

chunk 来源：

- `knowledge_items.content`
- `review_qa_pairs.question + answer_summary + issue + improvement`
- `review_insights.content`
- `review_transcripts.clean_text` 中的重要片段
- `resumes.structured_profile` 中的项目经历和技能证据
- `job_descriptions.structured_requirements` 中的岗位要求

注意：embedding 维度取决于使用的 embedding 模型。确定模型前不要随便定死维度。常见做法是：

```txt
embedding_model = 当前 embedding 模型名称
embedding vector(1024/1536/2048 等模型对应维度)
```

## 7. RAG 检索流程

模拟面试开始时，推荐流程：

```txt
输入：user_id、resume_id、job_id、interview_type

1. 读取用户画像 users / user_profiles
2. 读取当前简历 resumes
3. 读取目标岗位 job_descriptions / job_matches
4. 生成本次检索 query
   例如：数据科学岗 商业化算法 推荐系统 embedding 因果推断 项目深挖
5. 调用 embedding 模型，把 query 转成 query_embedding
6. 用 pgvector 从 knowledge_chunks 召回 TopK
7. 用 SQL 条件过滤 user_id、status、source_type、tags
8. 读取关联的 knowledge_items / review_qa_pairs / interview_reviews
9. 拼接模拟面试官 Prompt
10. 调用大模型生成定制化问题
```

检索 SQL 形态：

```sql
SELECT *
FROM knowledge_chunks
WHERE user_id = $1
  AND status = 'active'
ORDER BY embedding <=> $query_embedding
LIMIT 8;
```

实际生产中通常会混合过滤：

```sql
SELECT *
FROM knowledge_chunks
WHERE user_id = $1
  AND status = 'active'
  AND source_type IN ('review', 'resume', 'job')
ORDER BY embedding <=> $query_embedding
LIMIT 8;
```

如果要兼顾业务优先级，可以先向量召回 Top 50，再按优先级、来源、新旧程度重排。

## 8. 从复盘 JSON 抽知识库的规则

以当前 `_ai_review.json` 为例，可以这样抽：

### 8.1 高频问题

来源：

```txt
qa_pairs[].question
```

写入：

```txt
type = interview_question
title = 问题文本
content = answer_summary + issue + improvement
tags = topics
source_review_id = 当前 review
```

### 8.2 技术短板

来源：

```txt
qa_pairs[].issue
weaknesses[]
```

写入：

```txt
type = skill_gap 或 weakness
title = 短板标题
content = 证据 + 详细说明
priority = high -> 3, medium -> 2, low -> 1
mastery_level = weak
```

例如：

```txt
title = embedding 原理掌握不足
content = 缺乏对词嵌入、向量空间、训练目标的基本认知；面试中只能描述 SBERT 使用方式，不能解释底层机制。
tags = ["embedding", "向量空间", "SBERT", "推荐系统"]
```

### 8.3 改进建议

来源：

```txt
qa_pairs[].improvement
improvement_advice[]
next_actions[]
```

写入：

```txt
type = improvement_advice
title = 建议标题
content = 具体行动
next_review_at = 可按复习计划设置
```

### 8.4 回答模板

来源：

```txt
qa_pairs 中回答较好且可复用的问题
strengths[]
```

写入：

```txt
type = answer_template
title = 如何回答某类问题
content = 推荐回答结构
```

### 8.5 公司和岗位经验

来源：

```txt
metadata
interviewer 对岗位职责、团队工作、后续准备的说明
```

写入：

```txt
type = company_note
title = 腾讯音乐 数据科学岗面试关注点
content = 商业化算法落地、优惠券发放、ROI、LTV、推荐系统、因果推断、向量检索
```

## 9. 模拟面试 RAG 上下文拼接

当用户开始一次模拟面试时，推荐流程：

```txt
输入：user_id、resume_id、job_id、interview_type

1. 读取用户画像
2. 读取当前简历
3. 读取目标岗位 JD 和岗位匹配差距
4. 用 pgvector 从 knowledge_chunks 召回语义相关片段
5. 回查 knowledge_items / review_qa_pairs / interview_reviews 获取结构化来源
6. 拼接模拟面试官 Prompt
7. 生成第一批问题
8. 用户回答后继续结合历史短板追问
```

RAG 上下文示例：

```txt
用户历史短板：
- embedding 原理掌握不足
- 因果推断只了解 PSM/DID，缺少 Uplift / CATE / AB 实验设计
- 商业化建议能力弱，容易过度讲技术细节

历史真实面试高频问题：
- 什么是 embedding？如何把文本转成向量空间？
- 如何识别对发券响应最显著的用户？
- 如何评价因子的有效性？

本次模拟目标：
- 训练数据科学岗商业化算法落地表达
- 强化推荐系统、向量检索、因果推断追问
```

这样生成的模拟面试官才是“基于用户数据定制”的，而不是普通大模型面试官。

## 10. 当前数据库还缺什么

当前 schema 已经能支持面试复盘、问答、洞察和知识条目，但要做正式 RAG，还需要补：

```txt
knowledge_chunks
  -> 存 chunk 文本和 pgvector embedding

embedding_model
  -> 记录使用哪个 embedding 模型

retrieval_logs
  -> 记录某次模拟面试召回了哪些知识，便于调试
```

`knowledge_items.embedding_json` 可以废弃或仅保留为临时兼容字段。正式 RAG 不建议把 embedding 存 JSON 字符串，而应使用 pgvector 的 `vector(n)` 类型。

推荐新增：

```txt
knowledge_chunks
  id
  user_id
  knowledge_item_id
  source_type
  source_id
  chunk_text
  embedding vector(n)
  tags_json
  token_count
  status
  created_at

retrieval_logs
  id
  user_id
  mock_session_id
  query_text
  retrieved_chunk_ids
  created_at
```

Prisma 对 pgvector 字段通常要使用 `Unsupported("vector")` 或 raw SQL migration，向量检索也建议用 `$queryRaw` 执行。

## 11. 推荐落地顺序

建议按下面顺序做：

```txt
1. 安装 PostgreSQL + pgvector
   -> 创建 zhitou_copilot 数据库
   -> CREATE EXTENSION vector

2. Prisma 配置 PostgreSQL
   -> datasource provider = "postgresql"
   -> DATABASE_URL=postgresql://...

3. 补 knowledge_chunks 表
   -> embedding 使用 pgvector
   -> 常规业务字段仍由 Prisma 管理

4. 写 review 入库脚本
   -> 把 _ai_review.json、roles、clean_transcript 拆入 interview_reviews / review_transcripts / review_qa_pairs / review_insights

5. 写 knowledge 抽取脚本
   -> 从 qa_pairs、weaknesses、advice、knowledge_items 生成 knowledge_items 表
   -> 同时把可检索文本切成 chunks 写入 knowledge_chunks

6. 接入 embedding 模型
   -> 对 chunk_text 生成 embedding
   -> 写入 knowledge_chunks.embedding

7. 写 knowledge 查询接口
   -> GET /api/v1/knowledge/items

8. 写 RAG 检索接口 / 服务
   -> query -> embedding -> pgvector TopK -> 回查来源 -> prompt context

9. 写模拟面试上下文构建器
   -> 读取 resume + job + vector retrieved chunks + historical qa
```

一句话：

```txt
PostgreSQL 管业务关系。
pgvector 管语义召回。
knowledge_items 是可编辑知识条目。
knowledge_chunks 是 RAG 可检索片段。
```
