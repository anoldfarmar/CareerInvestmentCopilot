# 并行开发代码合并操作文档

本文用于处理当前两套开发环境并行开发后的代码合并问题：

- zpq：服务器运行后端和数据库，Windows 本机运行前端。
- ps：本机同时运行前端、后端和数据库。

目标是把双方一周内新增的功能、修复的 BUG、配置调整都合并到同一个集成分支中，确认前后端和数据库流程可用后，再合回主线分支。

## 一、合并前原则

1. 不直接在 `main` 上合并双方代码。
2. 双方先各自提交自己的当前工作，避免代码丢失。
3. 新建一个集成分支专门处理冲突和验证。
4. 冲突解决后必须跑完整前后端流程，而不是只看代码能不能提交。
5. 环境差异不要写死在代码里，统一使用 `.env` 或环境配置文件处理。

## 二、当前建议分支命名

```text
main                         稳定主分支
merge/zpq-server-work         zpq 服务器开发环境当前工作
merge/ps-local-work           ps 本机开发环境当前工作
integration/merge-week-work   本次一周并行开发集成分支
```

## 三、zpq 提交服务器侧当前代码

在服务器项目目录执行：

```bash
cd /home/CareerInvestmentCopilot-main
git status --short --branch
```

确认当前修改内容后，新建分支：

```bash
git checkout -b merge/zpq-server-work
```

提交当前工作：

```bash
git add .
git commit -m "save zpq server work"
```

推送到 GitHub：

```bash
git push origin merge/zpq-server-work
```

注意：如果有真实密钥、数据库密码、服务器 IP 等敏感信息，不要提交到 Git。真实配置应放在 `.env`，仓库中只保留 `.env.example`。

## 四、ps 提交本机侧当前代码

ps 在自己电脑的项目目录执行：

```bash
git status --short --branch
```

确认当前修改内容后，新建分支：

```bash
git checkout -b merge/ps-local-work
```

提交当前工作：

```bash
git add .
git commit -m "save ps local work"
```

推送到 GitHub：

```bash
git push origin merge/ps-local-work
```

如果本机有本地数据库配置、个人路径、Windows 专属配置，也不要直接写死进代码。需要和服务器环境区分的配置应放入环境变量。

## 五、新建集成分支

任意一方都可以执行，建议由负责合并的人在一份干净仓库中操作。

先切回主分支并更新：

```bash
git checkout main
git pull origin main
```

新建集成分支：

```bash
git checkout -b integration/merge-week-work
```

依次合并 zpq 和 ps 的工作分支：

```bash
git fetch origin
git merge origin/merge/zpq-server-work
git merge origin/merge/ps-local-work
```

如果第二次 merge 出现冲突，说明双方一周内改到了同一批文件或同一段逻辑，需要手动处理。

## 六、冲突处理方法

查看冲突文件：

```bash
git status
```

打开冲突文件后，会看到类似内容：

```text
<<<<<<< HEAD
当前集成分支中的代码
=======
正在合并进来的分支代码
>>>>>>> origin/merge/ps-local-work
```

处理原则：

- 如果是同一个 BUG 的两种修法：保留更完整、更符合现有代码风格的一版，也可以把两边优点合并。
- 如果是双方新增的不同功能：尽量都保留，检查路由、接口、组件名、数据库字段是否冲突。
- 如果是接口字段冲突：以后端真实返回结构为准，同时修改前端调用处。
- 如果是数据库结构冲突：统一模型和迁移文件，避免只在某一个人的本地数据库里存在字段。
- 如果是环境配置冲突：不要保留个人机器路径或写死 IP，改成 `.env` 配置。

解决完每个冲突文件后执行：

```bash
git add <冲突文件路径>
```

所有冲突解决后完成合并提交：

```bash
git commit
```

如果 Git 已经自动生成 merge commit message，可以直接保存退出。

## 七、重点检查清单

合并完成后，重点检查以下位置：

```text
1. 前端接口 baseURL 是否写死为 localhost 或服务器 IP
2. 后端接口路径是否被双方改成了不同版本
3. 数据库 schema、migration、初始化 SQL 是否一致
4. 新增页面是否已经接入路由和菜单
5. 新增接口是否有鉴权、参数校验和错误处理
6. package.json / lock 文件是否包含双方新增依赖
7. .env.example 是否补充了新增环境变量
8. Docker / GitHub Actions / 部署脚本是否仍然可用
```

## 八、合并后本地验证

先检查代码状态：

```bash
git status --short --branch
```

安装或更新依赖。按项目实际包管理器执行，例如：

```bash
npm install
```

或：

```bash
pnpm install
```

启动后端、数据库和前端后，至少验证这些流程：

```text
1. 登录 / 注册
2. 首页和主要页面是否能正常打开
3. zpq 本周新增功能
4. ps 本周新增功能
5. 双方都修过的 BUG 点
6. 前端调用后端接口是否正常
7. 数据库写入、查询、更新是否正常
8. 页面刷新后登录态和关键数据是否正常
```

## 九、推送集成分支

确认集成分支可以运行后，推送到 GitHub：

```bash
git push origin integration/merge-week-work
```

建议在 GitHub 上创建 Pull Request：

```text
integration/merge-week-work -> main
```

由双方一起检查改动，确认没有遗漏功能和环境配置问题后，再合并到 `main`。

## 十、后续协作建议

之后建议统一使用以下分支流程：

```text
main       稳定可演示版本
dev        日常集成版本
feature/* 个人新功能分支
fix/*      BUG 修复分支
```

日常开发流程：

```bash
git checkout dev
git pull origin dev
git checkout -b feature/your-feature-name
```

开发完成后：

```bash
git add .
git commit -m "add your feature"
git push origin feature/your-feature-name
```

然后通过 Pull Request 合并到 `dev`。需要演示或部署时，再从 `dev` 合并到 `main`。

这样可以减少一周后集中爆发的大冲突，也方便区分“功能开发问题”和“环境配置问题”。
